# BENI Complete Location System Audit

**Audit date:** 2026-10-21
**Project inspected:** `C:\Users\Vikram\Documents\Repositories\beni\beni`
**Mode:** Read-only source review. No code or database changes, migrations, data writes, resets, or dependency changes were made.

## Executive summary

Location support is limited to (1) optional manually entered coordinates and postal address details on a shop, (2) per-order delivery-address snapshots, and (3) a text address/locality saved on each repair booking. There is no reusable customer address record, worker service-area model, worker/customer GPS storage, geocoding, map, proximity search, or live worker tracking.

Shop and order/booking relationships are set from the signed-in user or the resolved shop/booking in server-side workflows. Shopkeeper edit and customer order/booking routes are owner-scoped. Assigned workers can see booking text addresses in their work queue. That address remains in an assigned booking record, and the worker queue has no status filter; the reviewed template continues rendering the address after completion/cancellation. No explicit address-sharing consent or disclosure record was found.

Status labels below use the requested vocabulary. **VERIFIED WORKING** is reserved for behavior supported by executable tests or equivalent direct evidence; the presence of a model/form/template alone is not treated as proof of end-to-end behavior.

## Staged implementation plan (not implemented)

1. **Approve product/privacy decisions before schema work.** Specify whether customer addresses are reusable records, transaction snapshots, or both; who can see shop street addresses; when repair addresses become visible to workers; whether to hide/revoke them after a status transition; and whether live worker tracking is actually required.
2. **Design location data separately by purpose.** If reusable customer addresses are needed, add an address entity owned by the auth user. Keep order/booking snapshots where historical fulfillment records require them. Define worker service coverage independently of any live position. Decide coordinate provenance, optionality, retention, and allowed precision.
3. **Obtain separate approval for schema/migrations.** Potential changes: customer address table and owner FK; optional coordinate pair on addresses and/or shops with paired-presence and geographic-range checks; structured worker coverage-area fields/model; and, only if approved, a short-lived booking-scoped live-location record with update timestamps/expiry/consent state. No migration was created or run during this audit.
4. **Implement safe forms and capture paths.** Add address validation, authenticated owner-scoped CRUD/selection, edit prepopulation and save/reload tests. Keep manual entry available. If GPS is approved, use an explicit opt-in action, validate browser results server-side, handle denied/unavailable/timeout/error states, and never fabricate coordinates.
5. **Add proximity behavior against persisted data.** Define matching/radius rules and implement queries using real stored coordinates/service areas. Specify behavior for missing coordinates and no results. Add tests for correct inclusion/exclusion, ordering, radius boundaries, and missing data before exposing “nearby” claims in UI.
6. **Add maps only after provider/privacy approval.** Reuse the chosen integration only after deciding whether it is necessary. Keep private keys server-side; use only appropriately restricted public keys in browser integrations. Handle provider/network/API failures without breaking manual address workflows.
7. **Add authorization and lifecycle controls before live GPS.** If live tracking is approved, require worker consent, limit collection to an explicitly active relevant booking, restrict reads to authorized participants, reject unrelated booking IDs, enforce freshness/expiry and stop tracking on completion/cancellation, and audit transitions. Test spoof/stale input handling and unauthorized access.
8. **Validate release state separately.** After approved schema changes, review generated migration operations, obtain deployment approval, then verify migration/model/database consistency using the project's established database-safety procedure. Do not perform those operations as part of this audit.
