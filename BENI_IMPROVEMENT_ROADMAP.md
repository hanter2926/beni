# BENI Marketplace Improvement Roadmap

**Scope:** Read-only review of the current Django source, existing audit reports, registered Admin modules, test definitions, templates, and static assets.  
**Project:** [`beni/`](./beni/)  
**Source reports reviewed:** [`BENI_CURRENT_STATUS_AUDIT.md`](./BENI_CURRENT_STATUS_AUDIT.md), [`BENI_LOCATION_AUDIT.md`](./BENI_LOCATION_AUDIT.md), and [`BENI_DATABASE_LOCATION_COMPARISON.md`](./BENI_DATABASE_LOCATION_COMPARISON.md).

## Verification boundary

This roadmap does not change application code, migrations, dependencies, or the database. It does not execute the SQL dump or connect to a database. The current-status audit reports a read-only configured-database check dated 2026-10-21, but that is prior evidence, not a fresh check in this task. The dump comparison concerns an older dump and is not evidence of the currently configured database.

Tests listed below are existing test definitions inspected in source. They were **not run for this documentation-only task**. The current-status audit likewise says its tests, browser workflows, MySQL concurrency, uploads, Razorpay sandbox, and deployment workflows were not exercised. Classifications therefore reflect the available implementation and evidence—not a claim of a passing release or production workflow.

The older location report describes worker service addresses as visible to assigned workers after a booking ended. Current source has since added `RepairBooking.worker_can_view_service_address`, a terminal-status visibility restriction, corresponding template logic, and regression tests. This roadmap uses the current source for that point; it does not treat that behavior as a fresh test pass.

## Dependencies

- Deployment hardening and a dedicated staging environment come before any public/live acceptance testing.
- Refund policy and provider refund handling depend on the existing payment/order lifecycle and must be defined before a payout/settlement system.
- Earnings and payouts depend on agreed marketplace commissions, order/repair completion triggers, refund treatment, and bank-data security policy.
- Repair quotes/invoices depend on pricing authority, customer acceptance, tax treatment, dispute handling, and payment/refund decisions.
- Worker matching depends on defined availability and service-area semantics. Any location collection additionally depends on explicit consent, access, retention, and accuracy rules.
- Customer address-book and proximity work depends on approved address/location schema and the policy for sharing full service addresses.
- Identity-provider integrations depend on approved vendors, legal basis, data minimization, retention, and document-handling decisions.
- Complaint handling and content/review operations depend on staff ownership, escalation/response expectations, and abuse/moderation policy.

## Phased implementation plan

| Phase | Scope and prerequisites | Required tests and acceptance criteria |
|---|---|---|
| 0. Production-safe staging baseline | Before public rollout. Confirm HTTPS/reverse-proxy topology and hosting choices. Resolve reported deployment warnings without weakening current auth/private-file checks; configure static and private media serving, environment-secret policy, dependency installation, backups, and operational logs/alerts. | Run Django deployment/system checks in the intended staging configuration and record zero unresolved release-blocking warnings or documented exceptions. Verify HTTPS redirects/cookies/HSTS in the real topology, static collection, private media denial through direct/public paths, authorized download access, backup restore, and smoke tests. Do not expose secrets in logs. |
| 1. Commerce and refund lifecycle | Depends on Phase 0 and an approved full/partial, per-order/per-checkout refund policy, staff authority, timing, and failure handling. Extend existing `payments`/`orders` architecture rather than creating parallel payment flows. | Unit tests for idempotent refund requests, authorization, duplicate/out-of-order callbacks, partial/multi-shop allocations, provider failure/retry, refund event verification, and order/payment state invariants. Run provider sandbox acceptance for success/failure and reconcile persisted amounts/references. Customer-facing status must not claim refunded until provider confirmation. |
| 2. Repair commercial lifecycle | Requires pricing/quote authority, labor/parts representation, customer acceptance/rejection, tax treatment, dispute/cancellation rules, and payment/refund policy. Then design any schema/migrations separately. | Tests for quote creation/edits by authorized worker, customer acceptance only by booking owner, immutable accepted quote, totals/tax calculation, invoice access scope, payment/refund state transitions, dispute path, and no charges without acceptance. Confirm support/admin history remains intact. |
| 3. Settlement and payouts | Depends on Phases 1–2 and approved commission/settlement rules, payout provider/bank policy, and reconciliation operations. | Ledger tests for idempotent earning credits, reservation/release/debit consistency, concurrent withdrawals, authorization, insufficient balance, payout success/failure/retry, reconciliation, and immutability. Test with provider sandbox; never derive a payable balance from UI-only state. |
| 4. Repair dispatch, availability, and location | Define worker availability and service-area format first. Decide customer address reuse, exact address disclosure, consent/retention, GPS necessity, and radius semantics before schema/provider work. Reuse booking and shop architecture. | Tests for eligible worker matching with genuine saved data, missing/incomplete coordinates, boundary/radius correctness, and no fabricated results. If live GPS is approved: explicit consent, request only while relevant booking is active, assigned-participant/staff authorization, stale/future/spoofed update rejection, and stop/expiry after terminal state. Browser tests for permission denied, unavailable GPS, timeout, and provider/API failure. |
| 5. Verification and trust operations | Decide manual versus provider-backed checks, allowed claims/labels, privacy retention, and staff review ownership. Define complaint/safety response, escalation, and resolution expectations. | Tests for application ownership, staff-only decisions/documents, re-submission/audit trail, provider failures if added, least-privilege access, complaint participant scope, staff escalation/resolution, notifications, and audit history. Verify no private identity data leaks through logs, Admin list displays, or public endpoints. |
| 6. Content, reviews, and customer-experience acceptance | Seed only real approved content; define moderation staffing and public review/appeal rules. No invented guide content or ratings. | Tests for contributor submission/publication and moderation permissions; review eligibility, uniqueness and disclosure; report handling; empty states. Browser and accessibility checks at phone/tablet/desktop sizes for keyboard navigation, focus, contrast, labels, error messages, loading/empty states, and responsive layouts. |
| 7. Release regression and operations | Depends on completed feature phases and staging baseline. | Run focused then full test suites in an isolated test DB; verify migration drift/plan read-only before separate deployment approval, without applying migrations during validation. Run MySQL-backed concurrency tests, end-to-end browser checkout/booking/support flows, webhook replay tests, upload lifecycle tests, and operational rollback/recovery rehearsal. Record actual environment and results. |

## Changes requiring separate approval

No schema or provider changes are proposed as part of this roadmap. Obtain explicit approval before:

1. **Database/schema and migrations:** customer address-book records; worker coverage/availability; live GPS and consent/retention records; repair quote, acceptance, invoice, tax/payment records; refund records/events; payout requests/settlement ledger writes; or additional complaint resolution/audit fields.
2. **External services or paid configuration:** Razorpay refund/payout APIs beyond the existing order-payment integration; map/geocoding/GPS providers; OTP/identity/face/bank-verification services; email/SMS/push delivery; storage, hosting, monitoring, or other paid services.
3. **Business/legal policies:** commission and settlement schedule; full/partial refund authority and timing; repair pricing and tax rules; worker tracking consent and retention; address disclosure; identity evidence retention; complaint SLAs and appeals.

## Recommended next implementation task

**Establish and verify a production-safe staging baseline before implementing new transaction or location features.** This should be the first bounded implementation task because the latest audit reports active deployment warnings and no verified production static/private-media topology, while the planned refund, payout, verification, and location work handles sensitive financial or personal data. Confirm the intended HTTPS/proxy and hosting configuration with the project owner before changing deployment settings; then validate it in staging without applying unapproved schema changes.
